1. 运输层的作用#

1.1 运输层的作用#

TIP

运输层向它上面的应用层提供通信服务，它是面向通信部分的最高层，是用户功能的最底层。

TIP

网络通信的两个端点是两台主机的进程。

运输层一个很重要的作用是复用(multiplexingmultiplexingmultiplexing)和分用(demultiplexing)demultiplexing)demultiplexing)。

运输层还需要对报文进行差错检测。

和一般的网络分层次一样，运输层为上层屏蔽了下面网络核心的细节，它使上层也只看见数据在两台主机的运输层平行传输。

定义1.1.11.1.11.1.1 两个对等运输实体在通信时传送的数据单元叫做运输协议数据单元(Transport Protocol Data Unit)TPDU，对应在TCP/UDP协议下叫做TCP数据段(segmentsegmentsegment)/UDP用户数据报。

1.2 运输层的端口#

需要有一种和操作系统无关的方式来标识主机间的进程，这种方式也就是在运输层使用协议端口号(Protocol Port Number)。数据报被传送到某台主机运输层的端口上，接着由运输层完成分用，把该数据交给对应的进程。

TCP/UDPTCP/UDPTCP/UDP的端口都使用161616位二进制数0−655350-655350−65535，端口号只具有本地意义，是应用层各个进程和运输层交互的一个层间接口。是一个软件接口。

其中1∼10231\sim 10231∼1023叫做**熟知端口号(well-known port number)**或者系统端口号，固定分配给一些特定的应用进程。

而1024∼491511024\sim 491511024∼49151 叫做登记端口号，给没有熟知端口号的服务器进程使用

49152∼6553549152\sim 6553549152∼65535叫做短暂端口号，一般给客户端进程暂时动态选择使用。

2. UDPUDPUDP#

2.1 UDPUDPUDP的特点#

UDPUDPUDP的特点主要有:

  1. UDPUDPUDP是无连接的协议，发送数据之前无需连接，也不需要关闭连接
  2. UDPUDPUDP是尽最大努力交付的，不保证可靠地交付
  3. UDPUDPUDP是面向报文的，每当上层交付一个数据报文，加上头部后就直接交付给IPIPIP层。不拆、不合并，不改变该数据报文的边界。每当从IPIPIP层接收一个数据报，去掉头部后就直接交给上层。一次交付一个完整的报文。
  4. UDPUDPUDP没有拥塞控制功能。
  5. UDPUDPUDP支持一对一、一对多、多对一、多对多的通信方式。
  6. UDPUDPUDP的头部开销非常小，只占**888个字节**。
CAUTION

由于UDPUDPUDP面向报文，因此上层交给UDPUDPUDP传输的报文必须要控制好大小。太大的报文在UDPUDPUDP交给IPIPIP层时，IPIPIP层一定要经过分片，效率很低。太小的报文会使得报文首部的比例占比过大，导致传输效率不高。

TIP

UDPUDPUDP没有拥塞控制，这意味着即便网络拥塞时数据的传输速率也不会变小。一方面这对实时性应用进程是好事，但是另一方面没有拥塞控制的UDPUDPUDP可能会引起网络的严重拥塞问题。

另外应用进程可以根据自己的需要，在传输层的上层为UDPUDPUDP自行添加一些提高可靠性的措施。

3. TCPTCPTCP#

3.1 TCPTCPTCP的特点#

TCPTCPTCP的主要特点有：

  1. TCPTCPTCP是面向连接的，通信前需要建立连接，最后需要释放连接。
  2. TCPTCPTCP提供可靠的交付服务
  3. TCPTCPTCP面向字节流，而不是面向报文。即便应用进程和TCPTCPTCP交互是一次一个数据块，但是TCPTCPTCP只把这些数据视为一连串的无结构字节流。
  4. TCPTCPTCP拥有拥塞控制功能。
  5. TCPTCPTCP只支持点对点、一对一的通信(TCPTCPTCP​需要建立虚连接，有两个端点)。
  6. TCPTCPTCP头部有202020个字节。
  7. TCPTCPTCP​提供的通信是全双工的。
CAUTION

TCPTCPTCP​协议的每一个端口都设有发送缓存和接收缓存，因此理论上进程可以在想发送的时候就发送，发送时也可以接收，是一条全双工的通信链路。

每当进程要发送数据时就会将数据放入发送缓存，接着进程就可以继续做自己的事情，由TCPTCPTCP在合适的时候发送。[可能是等缓存满了、pushpushpush操作、超时]

因而面向字节流的TCPTCPTCP​并不能保证接收方收到的数据块和发送方发送的数据块的划分是一样的，但是接收方收到的字节流和发送方发送的一定是一致的。

接收方的接收进程一定要能识别这个被重新划分的字节流。

3.1.2 TCPTCPTCP的连接#

TCPTCPTCP把连接作为最基本的抽象。

TCPTCPTCP的连接是端点到端点的连接。每一个端点都是一个SocketSocketSocket套接字，因此一个TCPTCPTCP连接也可以表示为:

TCP连接:={Socket1,Socket2}={(IP1:Port1),(IP2,Port2)}TCP连接:=\{Socket_1,Socket_2\}=\{(IP_1:Port_1),(IP_2,Port_2)\}TCP连接:={Socket1​,Socket2​}={(IP1​:Port1​),(IP2​,Port2​)}

也就是TCPTCPTCP连接的四元组。

TCPTCPTCP要建立的是可靠的通信信道，主要要实现的功能是:

  1. 信道不产生差错 [确认与重传机制]
  2. 发送方发送的数据接收方必须都能及时处理，(发送方和接收方的速度要匹配) [流量控制]

有一系列的协议用来解决这两个重要的问题。

3.3 TCPTCPTCP可靠传输的实现方式#

3.3.1 TCPTCPTCP的重传机制#

由于TCPTCPTCP有超时重传机制，但是超多少时间TTT才重传的时间TTT很难确定。

TTT过大导致接收方一直等待重传数据，空闲时间边长，效率很低

TTT过小导致发送方不断进行不必要的重发，效率也很低。

希望这个TTT仅仅只比往返时间RTTRTTRTT稍微长一些。使用每一次往返报文的RTTRTTRTT样本值来动态更新网络的往返时间RTTsRTT_sRTTs​:

RTTS(新)=(1−α)⋅RTTS(旧)+α⋅RTTRTT_{S(新)} = (1-\alpha)\cdot RTT_{S(旧)} + \alpha\cdot RTTRTTS(新)​=(1−α)⋅RTTS(旧)​+α⋅RTT

一般取α=0.125\alpha = 0.125α=0.125。

也是用该样本RTTRTTRTT来更新往返时间的方差RTTDRTT_DRTTD​:

RTTD(新)=(1−β)⋅RTTD(旧)+β⋅∣RTTS(新)−RTT∣RTT_{D(新)} = (1-\beta)\cdot RTT_{D(旧)} + \beta \cdot |RTT_{S(新)} - RTT|RTTD(新)​=(1−β)⋅RTTD(旧)​+β⋅∣RTTS(新)​−RTT∣

一般取β=0.25\beta = 0.25β=0.25。

重传时间RTORTORTO就取:

RTO=RTTS+4×RTTDRTO = RTT_S + 4\times RTT_DRTO=RTTS​+4×RTTD​

但是考虑到一种特殊的报文： 重传报文。如果一报文的确认并未收到，于是重发。重发后收到确认信息。

该确认信息如果是重传报文的确认却被认为是最初报文的确认，则会导致该RTTRTTRTT样本偏大，导致重传时间也偏大；但如果该确认信息是最初报文的确认却被认为是重传确认，则会导致该RTTRTTRTT样本偏小，算出的重传时间RTORTORTO也偏大了。判断该确认很麻烦，导致计算也很麻烦。

于是改进后的算法中对于重传报文的确认是这样使用的：

  1. 重传报文的RTTRTTRTT样本一律不采用

但是又出现了一种情况： 网络状况突然变得很不好，所有报文都要重传！这又导致重传时间不会更新，所以整个网络一直处于重传中。。。

再次更新算法：

于是改进后的算法中对于重传报文的确认变成这样使用：

  1. 重传报文的RTTRTTRTT​样本一律不采用
  2. 每次重传以后，取RTO(新)=γ⋅RTO(旧)RTO_{(新)} = \gamma \cdot RTO_{(旧)}RTO(新)​=γ⋅RTO(旧)​，一般取γ=2\gamma = 2γ=2。

实践证明，这样就合理了。。。

3.3.2 TCPTCPTCP​的发送/接收窗口#

3.3.2.1 发送窗口#

发送窗口指的是: 在没有接收到确认的情况下，能够发送出去的数据的字节数。

任何已经发送但是没有收到确认信息的数据，都要先放在发送方的发送缓存里。

接收方BBB的接收窗口一定比发送方AAA的发送窗口要小。

发送窗口有3个指针：

P1P_1P1​: 发送窗口后沿[可以发送的第一个字节可以发送的第一个字节可以发送的第一个字节]

P2P_2P2​: 第一个还没有发送的字节

P3P_3P3​: 发送窗口前沿[不能发送的第一个字节]

P2−P1P_2 - P_1P2​−P1​: 已经发送但还没有被接收的字节数

P3−P1P_3 - P_1P3​−P1​: 发送窗口大小

P3−P2P_3 - P_2P3​−P2​: 还可以发送但是尚未发送的字节数

发送窗口的后沿和发送缓存重合。(已确认的立刻删除)

发送窗口保存的是：

  1. 要发送但是还没发送的数据
  2. 已经发送但是没有收到确认的数据

3.3.2.2 接收窗口#

接收窗口保存的是：

  1. 已经连续确认但是没有被读应用进程取走的数据
  2. 未按序到达确认的数据

接收方BBB的每个确认值都是当前没收到的第一个字节的序号。

接收确认一般使用累积确认，这样可以减小网络传播开销。选择合适的时间把确认信息传递给对方，比如累积一定的确认、在发送自己的数据时捎带上确认信息。

3.3.3 TCPTCPTCP的流量控制#

TCPTCPTCP​​​的流量控制也是用接收窗口/发送窗口来控制。

CAUTION

当接收方告诉发送方发送窗口wnd=0wnd = 0wnd=0时就不允许发送方在发送数据。但是万一要发送的数据仍然没有发送完毕，发送方就会一直以为发送窗口仍然是0，哪怕接收方已经处理好了缓存。

一个解决办法是： 设置一个0窗口等待计时器，当计时器计时结束后发送一个0窗口探测报文，接收方在对该探测报文的确认中给出自己的窗口值。非0则可以传送数据，为0则重置等待计数器！

:::tip thinking

由于TCPTCPTCP报头至少是202020字节，IPIPIP数据报头又是202020字节，如果发送一个字节的数据，并且要求确认，线路上至少要传递1+20+201 + 20 +201+20+20 + 20+20=8120 +20 = 8120+20=81[假设确认消息不需要发送数据部分]。如果要求接收方也要发送一个字节的确认数据，且不采用捎带确认和累积确认，则这一个字节的数据也需要共818181个字节，只传送一个字节则需要一共162162162字节，444​个数据报。

但是如果使用捎带确认信息，则发送确认数据时可以把第一个数据报的确认也捎带，一共只需要333个数据报，41+41+40=12241+41+40 = 12241+41+40=122字节。

可见捎带确认和累积确认对减轻网络阻塞和提高利用率都很重要。

另外TCPTCPTCP报文数据段也不宜太短，最好是累积一些数据以后再一起发送出去。

:::

发送方一般采用NagleNagleNagle算法：

  1. 只有当前一个发送出去的数据报得到确认以后，再把缓存中的所有数据装成一个数据报发送出去。第一次只发送最初缓存中的第一个字节。
  2. 当数据已经达到窗口大小的一半或者最大长度时，就立刻发送一个数据报。
CAUTION

考虑一种情况：网络速度很快但是接收方处理非常慢——糊涂窗口综合征

极端情况下每一次发送/确认(一个RTTRTTRTT的时间)，接收方只能处理111个字节，确认信息中会告诉发送方只能有111个字节的发送窗口，发送方就会每次只发送一个字节，造成传输效率不高。
